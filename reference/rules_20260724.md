## R2 — 重大變更前 GitHub 備份 / GitHub Backup Before Major Changes

```
當前後版本的 openspec requirement 數量相差大於 25%，
必須先開一個新的 branch 保存上一版，再繼續進行。
When the requirement count across openspec/specs/ changes by more
than 25% between versions, a new branch must be created to preserve
the previous version before continuing.
```

**衡量方式 / Measure**：以 `openspec/specs/**/spec.md` 內 `### Requirement:` 的總數對比前一版，取代任意拆分的 task 數量，避免拆分粒度不同造成衡量失真。**本專案基準 / Baseline**：v1.1 生效時共 0 條 requirement（專案處於初始規劃階段）。`form-autofill-mvp` 變更中的 25 條 requirement 為 delta，依 R3 在歸檔前不計入基準。

**備份方式 / Backup method**：開新 branch（`git checkout -b backup/v<version>`）。

```
目前 0 條 requirement（初始階段），首次建立 specs 後
若後續變更預計新增/移除需求，以 25% 為門檻判斷

    ┌──────────────────────────────┐
    │  先開 branch 備份現有規格      │
```

## R3 — 文件同步紀律 / Documentation Sync Discipline

```
每次對以下檔案有更動時，必須仔細記錄並同步更新：
```

| 文件 / Document | 說明 / Description |
|---|---|
| `proposal.md` | 變更提案 / Change proposal |
| `tasks.md` | 任務清單 / Task list |
| `openspec/specs/**/spec.md` | 規格定義 / Specifications |
| `design.md` | 設計文件 / Design document |

**原則 / Principle**：不允許「程式碼先寫，文件之後再補」。每一次 commit 或 change 完成前，先確認四者一致。

**本專案補充（真實來源治理）**：本專案有兩層文件，各自的權威範圍不同，出現落差時依此順序判斷：

1. **`openspec/specs/**/spec.md`**（規則生效日起）— 系統行為的權威來源（source of truth）。任何 requirement/scenario 層級的行為定義，以此為準；程式碼與此處不一致時，以此處為準，除非該落差本身就是待修正的 bug。
2. **`PRD.md`** — 專案初期的高層需求總覽（系統架構、功能模組、非功能性需求），保留作為歷史脈絡與非正式速查，不再是逐條驗收依據；與 `openspec/specs/` 衝突時以 `openspec/specs/` 為準。

**本專案補充（避免文件分裂）**：不應同時維護兩份內容相近的規格文件並各自獨立修改。`openspec/specs/` 一旦建立，即為各能力的單一正本，`PRD.md` 不再視為需要逐條跟進的規格來源，僅保留為歷史文件。

**本專案補充（欄位契約的歸屬）**：`content-script` 與 `backend-api` 之間傳遞的欄位結構（field schema / answers / skipped）屬於跨能力契約，其權威定義放在 `openspec/specs/backend-api/spec.md`；`content-script` 的 spec 以 reference 之方式引用，不得各自定義一份。

## R4 — 討論優先於實作 / Discussion Before Implementation

```
任何更動都必須先討論，討論完畢並詢問確認後，才進行實作。
Any change must be discussed first; only after discussion is
complete and confirmed should implementation begin.
```

**流程 / Workflow**：

```
討論 / Explore (/opsx:explore)
  │
  ▼
確認方向 / Confirm direction
  │
  ▼
建立變更 / Propose change (/opsx:propose)
  │
  ▼
審閱提案（proposal.md / design.md / tasks.md）
Review proposal
  │
  ▼
明確回覆「可以實作」
User confirms "ready to implement"
  │
  ▼
開始實作 / Start implementation (/opsx:apply)
```

🚫 禁止行為 / Prohibited:
- 聊到一半直接開寫 / Coding during discussion
- 沒有明確確認就實作 / Implementing without explicit confirmation
- 邊討論邊修改程式碼 / Modifying code while discussing

**本專案補充**：本專案安裝的指令為 `/opsx-explore`、`/opsx-propose`、`/opsx-apply`、`/opsx-archive`、`/opsx-sync`，非 v1.0 文件所寫的 `/opsx:explore` 冒號格式。方向存在多種合理選項、且選錯代價高（例如「敏感欄位要靠關鍵字清單還是靠 ML 分類」、「後端要不要加 schema 驗證函式庫」、「擴充功能端要不要引入 TypeScript 建置流程」這類決策）時，須明確詢問使用者，不可自行假設後直接建立大量文件。

## R5 — Commit 紀律 / Commit Discipline

```
每個 task 完成後就做一次 commit。
禁止一個 commit 包含多個不相關的 task。
```

**Commit message 格式 / Format**：

```
<type>(<capability>): <簡短描述>
<type>(<capability>): <brief description>
```

**Types**：`feat` | `fix` | `refactor` | `docs` | `chore`

**`<capability>` 範圍**：對齊 `openspec/specs/` 下的能力名稱（待建立後更新），本專案預計為：

| 能力 / Capability | 職責 / Responsibility | 對應檔案 / Corresponding files |
|---|---|---|
| `extension-ui` | Popup 觸發介面、Options 設定頁、`chrome.storage.local` 讀寫 | `popup.html`、`popup.js`、`options.html`、`options.js` |
| `content-script` | 掃描頁面表單欄位、擷取 label 與 options、執行回填 | `content.js` |
| `background-worker` | 訊息路由、讀取設定、組裝後端請求、逾時與錯誤處理 | `background.js`、`manifest.json` |
| `backend-api` | Node.js + Express 後端、組裝 Prompt、呼叫 LiteLLM、驗證回應 | `backend/`（server、prompt、llm client、validator） |

**範例 / Example**：
```
feat(extension-ui): 在 Options 頁新增後端網址與模型名稱設定欄位
feat(extension-ui): add backend URL and model name fields in Options page

fix(content-script): 修正 select 欄位填入不在 options 內的值導致無聲失敗
fix(content-script): fix select fields silently failing when value not in options

feat(backend-api): 新增欄位約束驗證，拒絕超出 maxlength 的回應值
feat(backend-api): add field constraint validation rejecting responses beyond maxlength

docs(rules): 將專案規則改為通用 HTML 表單自動填寫（v1.1）
docs(rules): rewrite project rules for generic HTML form auto-filling (v1.1)
```

## R6 — 不做的清單 / Anti-Patterns (禁止清單)

```
以下行為列入禁止清單，如發現應立即停止並討論替代方案：
```

| # | 禁止行為 / Prohibited Behavior | 原因 / Reason |
|---|---|---|
| 6.1 | 在 Content Script 或 Service Worker 中使用空 `catch(e) {}` 忽略 DOM 掃描或網路錯誤 | 忽略錯誤 = 未爆彈。目標網站改版或後端未啟動時會靜默失敗，使用者只會看到「完成」但欄位全空 |
| 6.2 | 直接修改 `node_modules/` 或任何建置產物目錄 | 變更不可追溯，且下次 build 會覆蓋 |
| 6.3 | 在沒有先讀取檔案的狀況下編輯（AI agent 適用） | 憑空猜測造成破壞 |
| 6.4 | 將 LiteLLM API Key 硬編碼於擴充功能原始碼；或將任何密鑰、Token、OAuth Client Secret 提交至 Git | 擴充功能原始碼可被任何人檢視，密鑰將永久外洩且難以回收。LiteLLM 金鑰**只允許**存在於後端服務的環境變數（見 R9） |
| 6.5 | 刪除 failing test 來讓執行通過 | 欺騙驗證 |
| 6.6 | 由 LLM 猜測並填寫身分／財務類敏感欄位（身分證號、護照號碼、信用卡號、Bank Account、CVV、密碼、安全碼、醫療／病歷編號） | 通用表單最大風險。LLM 沒有真實資料，填入的只會是幻覺值。使用者若未逐欄檢查就送出，可能造成實際金錢或法律損害。敏感欄位必須跳過並回報（見 R17.5） |
| 6.7 | 自動回填後未向使用者顯示逐欄結果摘要（哪些已填、哪些跳過、哪些需人工確認），或讓程式主動送出表單 | 本工具的輸出是「未經驗證的猜測」。沒有摘要等於要求使用者盲目信任；自動送出則完全剝奪使用者最後一道檢查。對應 `auto-fill-html_forms.md` 初版僅有 `sendResponse({ status })` 一句狀態文字的不足 |
| 6.8 | 未尊重欄位約束（`required` / `maxlength` / `pattern` / `type`（`email`、`number`、`date`、`url`））即填入值 | 產生格式非法資料，導致前端框架驗證失敗或提交時被瀏覽器截斷，使用者難以察覺資料已損毀 |
| 6.9 | 對 `select`、`radio`、`checkbox` 填入不在該欄位 `options` 內的值 | 瀏覽器對 select 會直接拒絕無效值並回退到空值（或保留原值），造成「LLM 有回應但欄位沒填」的無聲失敗，且錯誤難以重現 |
| 6.10 | 對 `textarea` 等自由文字欄位填入含明顯 AI 轉折詞（「總結來說」、「此外」、「不遺餘力」）的長文，未經後處理即回填 | 沿用 v1.0 去 AI 味精神的通用化版本。求職、申請、留言類長文欄位若帶明顯機械感，會直接影響使用者的實際結果 |

## R7 — 每條 Spec 都要有驗證標準 / Every Spec Must Have Verification Criteria

```
每個 spec 必須明確定義「怎麼知道做完了」：
```

**模板 / Template**：

| 欄位 / Field | 內容 / Content |
|---|---|
| 規格說明 / Description | 什麼功能 / What feature |
| 驗證方式 / Verification | 怎麼測、怎麼看 / How to test or observe |
| 完成條件 / Completion Criteria | 具體 observable 的結果 / Specific observable result |

**範例 / Example**（對應預計建立的 `content-script` 能力之「表單欄位掃描」requirement）：

| 項目 / Item | 內容 / Content |
|---|---|
| 規格 / Spec | Content Script 能從任意網頁正確掃描出所有可填寫欄位，並為每個欄位產生穩定識別碼 |
| 驗證方式 / Verification | 開啟一個含文字框、下拉選單、單選、多選、textarea 的測試頁，點擊 Popup 的「分析並填寫」後檢查 Service Worker Console，输出的欄位陣列應包含 `id` / `type` / `questionText` / `options`，且 `type="hidden"` 與 `type="submit"` 欄位**不應**出現 |
| 完成條件 / Completion | 所有可見可填欄位 100% 被納入且各有不重複的識別碼；`options` 為 null 時代表該欄位無選項；`questionText` 長度上限 100 字且為空時回傳空字串而非 `undefined` |

事實上，OpenSpec 的 `#### Scenario:`（WHEN/THEN）格式本身即是這個模板的結構化版本——每條 requirement 底下至少一個 scenario，即滿足本規則。

## R8 — Task 粒度假設 / Task Granularity Default

```
除非特別說明，預設每個 task 的實作範圍：
```

| 維度 / Dimension | 限制 / Limit |
|---|---|
| 檔案數 / Files | 1–3 個 |
| 行數 / Lines | ≤ 250 行純邏輯（不含註解、空行） |
| 時間 / Time | 單一 session 可完成 |

超過上述範圍 → 需拆分 task。

**本專案補充**：拆分 task 時對齊 `openspec/specs/` 的能力名稱與 requirement 名稱，並在 task 名稱或 commit scope 標註對應能力名稱（見 R5）。一個 task 不應橫跨過多不相關的能力——例如同時改動 `content-script`（DOM 掃描）與 `backend-api`（LLM 代理）的 task 應拆開，因為兩者的驗證方式（瀏覽器 DevTools vs. `curl` 打 API 端點）完全不同。

**本專案補充（後端檔案特別注意）**：`backend/` 建議至少拆為 `server`（Express 路由與啟動）、`prompt`（Prompt 模板組裝）、`llm`（LiteLLM 客戶端）、`validate`（回應驗證）四個檔案。Prompt 模板與 HTTP 路由若放在同一檔案，會讓後續調整 Prompt 時被迫觸碰無關的路由程式碼。

## R9 — 技術棧鎖定 / Tech Stack Lock

```
決定技術棧後，在 openspec/specs/stack.md 鎖定版本，
未經討論不得引入新的依賴（不分 major/minor）。
Once the tech stack is decided, lock versions in
openspec/specs/stack.md; no new dependency (major or minor)
may be introduced without discussion.
```

**鎖定項目 / Locked items**：

| 層次 / Layer | 技術 / Technology | 備註 / Notes |
|---|---|---|
| 擴充功能殼層 / Extension shell | Chrome Extension **Manifest V3** | Chrome 強制要求，不可降級 |
| 擴充功能權限 / Permissions | `activeTab`、`scripting`、`storage` | 對應初版 `manifest.json`；新增權限視為重大變更，需走 R4 |
| 擴充功能端語言 / Extension language | Vanilla JavaScript（無框架、無建置步驟） | 沿用初版 `auto-fill-html_forms.md` 的零相依作法。是否改用 TypeScript + Vite 屬待確認事項 |
| 設定儲存 / Settings storage | `chrome.storage.local` | 存放**非敏感**設定：後端 base URL、模型名稱、預設語言。**不存**任何 API Key（見 R6.4） |
| 後端執行環境 / Backend runtime | Node.js（版本待確認） | |
| 後端框架 / Backend framework | Express（版本待確認） | |
| LLM 整合 / LLM integration | OpenAI-compatible endpoint（LiteLLM `/v1/chat/completions`） | **僅由後端呼叫**，擴充功能端不直接連線 |
| 序列化 / Serialization | JSON over HTTP | 是否引入 schema 驗證函式庫（如 zod / ajv）待確認 |

**系統流程圖 / System Flow Chart**（2026-09-27 更新，反映 v1.1 專案轉向）：

```
使用者點擊瀏覽器工具列圖示 → Popup「分析並填寫 / Analyze & Fill」
      │
      ▼
Service Worker 讀取 chrome.storage.local
      │  取得後端 base URL、模型名稱
      │  防呆：設定未完成 → 提示使用者前往 Options 頁設定

Content Script 掃描當前頁面 DOM
      │  選擇器：input:not([type=hidden]):not([type=submit]):not([type=button])
      │          , textarea, select

Backend API Server（Node.js + Express）
      │  1. 驗證請求（欄位數上限、payload 大小）
      │  2. 組裝 Prompt（要求純 JSON 回應、選項須完全符合）
      │  3. 由環境變數讀取 LiteLLM 金鑰
      ▼
LiteLLM（OpenAI-compatible /v1/chat/completions，temperature 0.1）
      │  回傳 {"answers": {...}}
      ▼
Backend API Server（回應驗證）
      │  1. 解析 JSON（失敗 → 回傳可讀錯誤，非空物件）
      │  2. 逐欄比對 options：不在清單內的值丟棄並記入 skipped
      │  3. 檢查 maxLength：超長截斷或丟棄並記入 skipped
      │  4. 敏感欄位（見 R6.6）強制丟棄並記入 skipped
      ▼  { answers, skipped }
Content Script 執行回填 fillForm()
      │  radio / checkbox → 比對 value 後設 checked（陣列則多選）
      │  select          → 指派 value；選項不存在則跳過並記錄
      │  text / textarea → 指派 value（尊重 maxlength）
      │  每欄填入後 dispatch input / change 事件（相容 React / Vue）
      │  防呆：識別碼查無對應元素 → 跳過，不中斷整批
      │
      ▼
Popup 顯示逐欄結果摘要
      │  「已填入 N 欄；跳過 M 欄（敏感欄位 K 欄、選項不符 J 欄）」

      ▼
使用者逐欄人工審閱 → 自行按下頁面原有送出鈕
（本工具永不主動觸發 form submit，見 R6.7）
```

## R16 — 修復優先於新功能 / Fix-Before-Feature Priority

```
已知的缺陷、資安問題、或造成使用者可見功能失效的 bug，
優先於新增功能被排入開發順序，除非新功能本身就是修復所必需的架構調整。
```

**本專案對應機制**：改用「已知問題 vs. 新功能」排序：
- **優先**：已知的基礎功能失效問題（例如 Content Script 無法掃描到欄位、後端未啟動時無提示、識別碼對不上導致整批填入失敗、選項不符造成無聲失敗）應優先於任何新增能力的變更被實作
- **例外**：若新功能本身是修復的前置架構（例如需要先建立 `openspec/specs/stack.md` 才能安全新增依賴），可提前排入

**理由 / Reason**：基礎功能（掃描、傳送、呼叫 LLM、回填、顯示摘要）是整個系統的核心路徑，在此路徑穩定前投入新功能開發，會讓使用者面對一個根本無法正常運作的工具。

**本專案特別強調**：通用表單自動填寫會接觸使用者的**個人資料與敏感欄位**。任何造成錯誤填入的缺陷（例如識別碼碰撞、跳過邏輯失效），其危害等級高於一般 Web 應用，必須視為最高優先修復項。

## R17 — DOM 掃描與回填正確性紀律 / DOM Scanning & Filling Correctness Discipline

```
取自 reference/auto-fill-html_forms.md 初版程式碼的實作教訓。
任何掃描或回填邏輯的修改都必須遵守以下五點。
Drawn from the implementation lessons of the initial code in
reference/auto-fill-html_forms.md. Any change to scanning or filling
logic must comply with the following five points.
```

**R17.1 — 穩定識別碼 / Stable identifier**
```
每個被掃描到的欄位都必須有非空且在該次掃描中不重複的識別碼，
回填階段必須以識別碼反查元素，不得依賴 DOM 順序或 index。
Every scanned field must carry a non-empty identifier that is unique
within that scan, and the filling stage must look elements up by that
identifier — never by DOM order or index.
```
優先序：既有 `id` → 既有 `name` → 注入 `data-ai-id="ai_input_<index>"`。
反查順序：`getElementById` → `[name="..."]` → `[data-ai-id="..."]`；三者皆找不到時**跳過該欄位並記錄**，不得中斷整批填寫。

**R17.2 — 排除非輸入欄位 / Exclude non-input fields**
```
掃描選擇器必須排除 `type` 為 hidden、submit、button、image、reset、file 的欄位。
The scanning selector must exclude fields whose `type` is hidden,
submit, button, image, reset, or file.
```
`file` 排除的理由：瀏覽器出於安全限制不允許程式寫入 `input[type=file]` 的 value，初版未排除此類型會產生永遠填不成功的假成功。

**R17.3 — 事件派發 / Event dispatch**
```
回填後必須對每個元素派發 `input` 與 `change` 兩個事件（`bubbles: true`），
否則 React / Vue 等以狀態驅動的框架不會更新，使用者會看到值被清空或送出空值。
After filling, `input` and `change` events must be dispatched on every
element with `bubbles: true`, otherwise state-driven frameworks such as
React and Vue will not update and the user sees an emptied or empty
submitted value.
```
🚫 禁止：僅設定 `el.value` 就視為填寫完成。

**R17.4 — 選項白名單 / Option whitelist**
```
填入 `select`、`radio`、`checkbox` 的值必須先確認存在於該欄位的 `options` 集合中。
不存在的值一律跳過並記入 `skipped`，不得直接指派。
A value written into a `select`, `radio`, or `checkbox` must first be
confirmed to exist in that field's `options` set. Values that do not
exist are skipped and recorded in `skipped`, never assigned directly.
```
比對規則：`select` 用 `option.value`，並支援以 `option.text` 輸入、由程式轉換為 `value`；`radio` / `checkbox` 以 `el.value` 精確比對；多選以陣列處理，逐一比對後勾選命中項。

**R17.5 — 敏感欄位留空 / Leave sensitive fields blank**
```
識別為敏感類別的欄位（見 R6.6）不得填入任何值，一律記入 `skipped` 並在摘要中逐項列名，
交由使用者手動填寫。
Fields identified as sensitive (see R6.6) must not receive any value;
record them in `skipped`, list them by name in the summary, and leave
them for the user to fill in manually.
```
本專案的立場是「寧可少填，不可填錯」。跳過一個欄位的成本是使用者手動打十個字；填入一個幻覺身分證號的成本可能是法律問題。

## R18 — LLM 呼叫契約紀律 / LLM Call Contract Discipline

```
所有對 LiteLLM 的呼叫必須遵守以下契約。本條由初版程式碼的
prompt 設計與錯誤處理方式歸納而成，並補上初版缺失的安全考量。
All LiteLLM calls must comply with the following contract. This rule is
derived from the initial code's prompt design and error handling, with
the security considerations the initial version lacked.
```

**R18.1 — 純 JSON 回應 / Pure JSON response**
```
必須以 `response_format: { "type": "json_object" }` 要求 JSON 輸出，
`temperature` 設為 0.1，並在 Prompt 中明確禁止 markdown 程式碼區塊包裝。
回應解析失敗時必須拋出可辨識的錯誤並回報給使用者，
不得如初版般靜默回傳 `{}` 讓使用者誤以為「沒有可填的欄位」。
Must request JSON output via `response_format: { "type": "json_object" }`,
set `temperature` to 0.1, and state in the prompt that markdown code
fences are forbidden. A parse failure must raise a recognizable error
reported to the user — never silently return `{}`, which the user would
misread as "no fillable fields found".
```

**R18.2 — 選項必須逐字符合 / Options must match verbatim**
```
Prompt 必須明確要求：選擇型欄位的答案必須完全等於 `options` 中的字串，
不得改寫、翻譯、簡化或自行發明。
The prompt must state that answers for choice-type fields must be
exactly equal to a string in `options`, with no rewriting, translation,
shortening, or invention.
```

**R18.3 — 頁面內容視為不可信輸入 / Page content is untrusted input**
```
頁面上的欄位文字、label、option 文字、乃至 `parentElement.innerText`，
全部是第三方網站控制的內容，必須視為**資料**而非**指令**。
Prompt 中不得將這些內容提升為系統指令層級；後端亦須在回應驗證階段
再次以 `options` 白名單比對，不能只依賴 LLM 自律。
All page text — field labels, option labels, and even
`parentElement.innerText` — is controlled by a third-party site and
must be treated as data, never as instructions. The prompt must not
promote this content to the system-instruction tier, and the backend
must re-validate against the `options` whitelist rather than trusting
the LLM to self-police.
```

**R18.4 — 不得外傳頁面內容 / No exfiltration of page content**
```
送給 LiteLLM 的內容僅限完成填寫所必需的欄位結構描述。
不得將整頁 HTML、使用者 Cookie、網址中的 query token、或其他與填寫無關的
頁面內容送往後端或第三方模型。
Only the field structure needed to complete the form may be sent to
LiteLLM. Whole-page HTML, cookies, query-string tokens, and any other
page content unrelated to filling must never be forwarded to the
backend or to third-party models.
```

**R18.5 — 逾時與失敗必須可見 / Timeouts and failures must be visible**
```
後端對 LiteLLM 的呼叫必須設定逾時；逾時或錯誤時，Popup 必須顯示
可理解的錯誤訊息（依 R6.7 的摘要形式），不得顯示「處理完成」或靜默無反應。
Calls to LiteLLM must set a timeout; on timeout or error the popup must
show an understandable message in the summary form required by R6.7,
never a "process finished" message and never silence.
```

**R11（開發伺服器使用非標準 PORT）已移除，不納入本版**。原規則要求專案的開發伺服器禁止使用常見預設 Port，以避免與其他專案衝突。本專案後端 API 伺服器的 Port 由部署環境（雲端或本地）決定並透過環境變數 `BACKEND_PORT` 注入，非本專案的開發慣例所能控制；且擴充功能透過 `chrome.storage.local` 設定的 base URL 與後端通訊，Port 衝突風險極低，故直接移除而非改編。若未來本專案發展出本地開發伺服器（例如 mock API server），可再依當時實況新增對應規則。

### 情景 1：後端新增一個模型切換端點

```
變更: 在後端新增 POST /api/model 端點，讓 Options 頁可切換模型名稱

應該做:

✅ 依 R9，未引入任何新相依則不需更新 stack.md
✅ 依 R13/R14，同步更新 openspec/specs/backend-api/spec.md 與 R12 流程圖
✅ 依 R5，Commit message 標註 capability：feat(backend-api): 新增模型切換端點

不應該做:
❌ 只加路由，spec 與 R12 流程圖之後再補
❌ 順手在這個 commit 裡改動 content-script 的掃描選擇器
```

### 情景 2：頁面上有身分證號欄位

```
情境: 使用者在某政府網站的報名表單上點擊「分析並填寫」，
      頁面包含「身分證字號」欄位與「出生日期」欄位

應該做:
✅ 依 R17.5，「身分證字號」判定為敏感欄位，不填入任何值
✅ 依 R6.7，摘要顯示：「已填入 8 欄；跳過 1 欄（敏感欄位：身分證字號），請手動填寫」
✅ 依 R6.6，不對「出生日期」做 LLM 猜測——若無使用者提供的資料來源，應一併跳過

不應該做:
❌ 讓 LLM 生成一個格式正確的假身分證號
❌ 靜默跳過而不告知使用者，以為已填完
❌ 自動按下頁面的送出鈕
```
